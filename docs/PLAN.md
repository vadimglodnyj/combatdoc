## 1. Мета продукту

Система обліку військовослужбовців (НГУ, в/ч 3029), які лікуються / обстежуються в різних ЛПЗ.

**Цілі:**
- спростити роботу медика частини;
- вчасно й точно подавати в стройову (впливає на грошове забезпечення / додаткову винагороду);
- контролювати епізоди, сегменти лікування, ВЛК, довідку №5, оплату, задачі команди.

**Не робимо:** ЄСОЗ, портал «е-лікарняний» для цивільних, аптеку (поки відкладено).

## 3. Доменна модель

```
ServiceMember (картка в/с)
└─ Episode (справа по діагнозу)
   ├─ Consultation[]     # візити / обстеження + outcome-дерево
   ├─ CareSegment[]      # режими непрацездатності / обліку
   ├─ InjuryCertificate? # довідка №5 (для COMBAT)
   ├─ VlkDecision[]
   └─ JournalEntry[]     # append-only

Task / TeamMember         # Trello-подібний борд + Discord
PaymentPeriod             # виплачені / до виплати інтервали
Dictionary*               # звання, підрозділи, ЛПЗ, ролі лікарів…
```

### 3.1. ServiceMember (картка)

Поля: ПІБ, звання, тип служби, **повна посада**, підрозділ скорочено для чату (автогенерація, можна правити), ДН, телефон, ІПН (для ВЛК), військкомат призову, дата призову, освіта (рівень / заклад / місце / рік).

- Усі поля **редаговані** після імпорту.
- Excel / Turso = початкове заповнення, далі ручне редагування.
- На картці: активний епізод/сегмент, лічильник 120, PLANNED, кнопки генерації документів.
- Підпорядкування командиру — **не потрібне**.

### 3.2. Episode

- Одна справа по діагнозу; після «в строю» можна закрити.
- Рецидив того самого діагнозу → **reopen** того ж епізоду.
- **Характер:** `COMBAT` | `SOMATIC`.
- Лічильник **120 безперервних днів** рахує лише: `HOSP`, `AMB`, `VLK_LEAVE`, `REHAB`. Після перерви «в строю» — з останнього безперервного відрізка.
- Після ВЛК на тривале — контроль дедлайну **120+X**.

### 3.3. Довідка про обставини травми (№5)

Якщо `Episode.nature = COMBAT`:
- обов’язковий контроль документа `INJURY_CIRCUMSTANCES`;
- статуси: `MISSING` | `PENDING` | `VERIFIED` | `REJECTED` (UI: немає / на контролі / є / відхилено);
- без `VERIFIED` — жовтий/червоний індикатор на епізоді;
- **нагадування** (Tasks + Discord), поки немає підтвердженої довідки (довго роблять);
- завантаження PDF/фото **≠** автоматичне підтвердження:
  1. OCR;
  2. класифікація (ШІ / правила): чи це саме довідка про обставини травми;
  3. `PENDING` → підтвердження медиком або авто-`VERIFIED` за правилами;
  4. інакше `REJECTED` + задача «підкласти правильний файл»;
- **впливає на оплату** — без `VERIFIED` для COMBAT: блок / жорстке попередження в модулі оплати.

У старому Medhar: `treatments.cause`, `needs_injury_cert`, `injury_cases`, media `kind=injury_cert`, `circumstances_parser`, `gemini_extract`.

### 3.4. Consultation (замість окремих МПБ / направлення / консультація)

- Обов’язкові autocomplete: **facility** (ЛПЗ/МПБ) + **practitionerRole**.
- Популярність зверху + seed (МПБ, ДУ ТМО МВС Запорізька, ЗОКЛ, МЛЕ/ШМД, 9 міська; ролі: терапевт, хірург, травматолог, ЛОР, фельдшер/начальник МПБ…).
- `kind`: `VISIT` | `EXAM`; `status`: `PLANNED` | `DONE` | `CANCELLED`.
- Outcomes → дочірні PLANNED (`CONSULTATION` | `EXAM` | `CARE_SEGMENT`).
- Нагадування без дати + списки на дату + **Discord обов’язково**.
- Подача в стройову — **не** з Consultation, а з CareSegment (див. нижче).

> Окремий документ DOCX «направлення» — **не робимо**.

### 3.5. CareSegment

**Типи:** `HOSP`, `DAY`, `AMB`, `MPBR`, `REHAB`, `ABROAD`, `PHYS`, `VLK_LEAVE`.  
`STROJ` = немає активного сегмента.

**Поля:** patient/episode, тип, dateFrom/dateTo, facility, № документа, діагноз, примітка, фото, статус WhatsApp.

**Дії:** відкрити / продовжити (**лише AMB**) / закрити / перехід / подати в чат1+2.

**Матриця переходів (коротко):**
- майже всі типи ↔ усі інші через **перехід** (закрити A + відкрити B);
- AMB prolong = лише зсув `dateTo`;
- той самий тип / інший заклад = перехід, не prolong;
- `VLK_LEAVE` **не продовжують** (тривалість — інпут днів, підказки 30/60/120);
- виписка + відпустка: `HOSP.dateTo` = день виписки, `VLK_LEAVE.dateFrom` = **наступний день**;
- оверлеї ВЛК: придатність → авто `MPBR`; тривале +X без виписки; кастом «подальше лікування в ЛПЗ».

**120 днів:** HOSP + AMB + VLK_LEAVE + REHAB.

### 3.6. WhatsApp

Шаблон: підрозділ · ПІБ · звання+тип служби · ДН · телефон · **Дія** · діагноз (+ фото).

| Чат | Що |
|-----|----|
| Чат 1 (непрацездатність) | AMB / HOSP / відпустка ВЛК / ВЛК (коли впливає на облік/МПБр) |
| Чат 2 (командирам) | **усе**: і непрацездатність, і консультації |

Кнопка подачі — на Consultation/CareSegment, не головна на картці.

### 3.7. Documents (окремий модуль)

Генерація **і з картки без жодного звернення**, і з епізоду:

| Документ | Примітка |
|----------|----------|
| Медична характеристика | DOCX |
| Службова характеристика | DOCX |
| Рапорт на ВЛК | DOCX |
| Фабула на ВЛК | DOCX (у зразках заголовок ВЛК) |
| Рапорти інших типів | госпіталізація, консультація, матдопомога, оздоровлення, відпустка, реабілітація |
| Відомість обліку днів (Додаток 2) | стаціонар / реабілітація / відпустка за місяць |

**Не робимо:** DOCX «направлення».

Потрібні: відмінки ПІБ/звання, довідник підписантів частини.

### 3.8. Journal

Append-only у тій самій транзакції, що зміна:
- клінічні події — з `patientId`;
- технічні (реєстрація, логін, ролі) — без `patientId`, для адміна;
- тип `NOTE` — **не потрібен**.

### 3.9. Tasks + Discord (обов’язково)

Аналог Trello зі старої системи:
- колонки `todo` / `doing` / `done`;
- assignee ↔ `team_members` (sync_id, discord_id);
- webhook і токени — **лише в секретах** (не в git / не в чаті відкритим текстом; webhook зі старого чату — перевипустити);
- нагадування: довідка №5, PLANNED на дату, довготривале, дедлайни задач;
- поліклінічний список на дату → Discord.

### 3.10. Оплата

Окремий модуль-калькулятор (не копія старого UI):
- джерела: CareSegment (стац / реаб / відпустка) + імпорт уже виплачених періодів з Excel;
- для COMBAT — перевірка `VERIFIED` довідки №5;
- вихід: відомість / DOCX за шаблоном + примітки.

### 3.11. Аптека

**Поки не чіпаємо** (поза поточним планом).

### 3.12. Контроль пацієнтів (екрани)

Порт логіки вкладок зі старого `/patient-control`:

| Вкладка | Зміст |
|---------|--------|
| Стаціонар | активні HOSP; обдзвін (у старому — після 10 днів) |
| Поранені | активні COMBAT-епізоди |
| Поліклініка | PLANNED на дату + Discord |
| ВЛК | черга / рішення |
| Довготривале | 120+ / 120+X |
| Нагадування | дедлайни ±N днів |
| Довідки | COMBAT без VERIFIED довідки №5 |

## 4. Імпорт даних (критичний шлях)

### Принцип
1. **Спочатку картотека**, потім звернення.  
2. Один SoT після імпорту = Postgres. Excel — разовий/періодичний імпорт, не live.  
3. Preview + звіт дублів / конфліктів; без тихого перезапису.  
4. Формули `#NAME?` — ігнорувати (data-only).

### Крок A — картотека зі Штат / KEY
Файл `base` (~693 рядки, підрозділи 1–6, посада, звання штат/факт, ПІБ, вид служби, скорочення, відрив) → `ServiceMember`.  
RKCH — шар відривів / уточнень.

### Крок B — merge з Turso `patients` (~470)
Матч: нормалізований ПІБ + ДН (fallback телефон).  
Збагачення полів картки; конфлікти — у звіт.

### Крок C — епізоди з Turso
`treatments` (~320) → Episode (`cause` → COMBAT/SOMATIC, `needs_injury_cert`, `injury_case_id`).  
`injury_cases` (~210) + media `injury_cert` → InjuryCertificate (+ шляхи файлів з Dropbox, якщо доступні).

### Крок D — сегменти / журнал
`outpatient_entries` (~929) → CareSegment / Consultation / Journal  
з мапінгом `care_type` → типи 2.0.

### Крок E — Excel «Санітарні втрати» (3 книги)
Дозаповнення прогалин: телефон, ДН, діагноз, вид лікування, ВЛК, бойова/небойова, **довідка №5**, виплачені періоди (де є колонки).  
Матч до картки; без картки → сира з міткою «не зі штату».

### Крок F — Tasks / Discord
`team_tasks`, `team_members`, `team_settings` (без секретів у відкритому вигляді).

### Крок G — оплата
Імпорт виплачених періодів з `data/payments/*.xlsx` + перерахунок «до виплати» правилами модуля.

**Не імпортуємо як обов’язкове для MVP:** pharmacy_*, Discord quiz.
